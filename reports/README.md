# Reports architecture

This folder provides combined, shareable reports that bring together data from
all of the Carbon & Place tools for a chosen area.

## Pages

| Page | Area type | Data key | URL |
|---|---|---|---|
| `lsoa.html` | Neighbourhood (LSOA / Data Zone) | `LSOA21CD` | `/reports/lsoa.html?lsoa=E01000001` |
| `la.html` | Local authority | `LAD25CD` | `/reports/la.html?id=E08000035` |
| `wards.html` | Electoral ward | `WD25CD` | `/reports/wards.html?id=E05011403` |
| `parishes.html` | Parish | `PAR23CD` | `/reports/parishes.html?id=...` |
| `constituencies.html` | Westminster constituency | `PCON24CD` | `/reports/constituencies.html?id=...` |

`index.html` is the landing page with search boxes for each area type (name
lookup data in `la.json`, `wards.json`, `parish.json`, `westminster.json`).
The homepage postcode search resolves a postcode to its 2021 LSOA via
postcodes.io and routes to `lsoa.html`.

## The LSOA report (`lsoa.html`)

Structure: *highlight first, dig deeper on demand*.

1. **Context** — ward/LA/constituency/parish names and the area classification,
   from `lsoa_overview` on the blob store.
2. **Highlights** — one native Chart.js chart per tool (carbon footprint,
   vehicle ownership, household energy), rendered immediately.
3. **"Show all charts"** — lazily loads the tool's *full report card*: every
   chart from the tool's popup modal (see below).
4. **Tool links** — each tool opens deep-linked via `?report=<code>`, and area
   summary report links are built from the codes in `lsoa_overview`.

## Shared report-card modules (`cards/`)

`cards/{pbcc,transport,retrofit}-card.html` + `.js` are **generated** copies of
each tool's zones report modal (its HTML fragment and its chart-building
JavaScript), so a report page can show *literally every chart* from the tool
without duplicating hand-written code.

- Generated by `make_report_cards.py` (kept in the developer scratchpad; also
  reproducible from this description). Inputs: `{tool}/index.html` (the
  `#zones-chartsmodal` modal body) and `{tool}/ui.js`.
- Transformations: all top-level identifiers are prefixed (`pbccCard_...`) so
  three tools can coexist on one page; `capUi.fetchJSON` is replaced by a local
  fetch helper; `alert()` becomes `console.warn()`; modal tab switching is
  scoped to the fragment; print/isochrone/tool-page-only code is stripped;
  and PBCC gains null-guards so missing comparison data degrades gracefully.
- Data endpoints are routed through an `…endpoint('<path>')` helper which
  honours `window.REPORT_CARD_ENDPOINTS = { '<default>': '<override>' }`.
  This is how area-level pages reuse the same cards against aggregated data,
  e.g. `{ 'vehicle_summary/v1/': 'ward_vehicle_summary/v1/' }`.
- **Regenerate whenever a tool's modal or chart code changes.** The tools remain
  the source of truth; the cards are build artefacts committed to the repo
  (there is no build system on deploy).

## Area-level reports

`la.html` and its siblings share one engine (`la-report.js`) configured by
`window.REPORT_CONFIG = { dataPath, level, nameJson }` for the emissions
charts, plus the same full-card sections as the LSOA report with
`REPORT_CARD_ENDPOINTS` pointing at area-aggregated data.

Aggregated data is produced by the R pipeline (`../build`):
- `make_{la,ward,parish,constituency}_summary` → per-capita emissions
  (`<level>_emissions`).
- `R/area_summaries.R` → transport/retrofit datasets aggregated to each level
  (`<level>_vehicle_summary`, `<level>_pt_frequency`, `<level>_access`,
  `<level>_epc_dom`, `<level>_gas_electric`).

**Aggregation methods**: counts are summed; rates and averages are recomputed
from summed numerators/denominators where possible, otherwise weighted means
(population weights for PT frequency, accessibility and vehicle rates; meter or
dwelling weights for energy and EPC averages). **Medians at area level are
weighted medians — an approximation** (a true median needs unit-level data) —
and are flagged as such wherever shown. Isochrones are point-based and are
deliberately **excluded** from area aggregation.

## Locator maps

Every report page shows a small non-interactive map of the reported area's
boundary (`area-map.js`, which lazy-loads MapLibre + pmtiles only when used).
Boundary data comes from one simplified GeoJSON per area, produced by
`../build/R/boundary_jsons.R` (`boundary_jsons_{lsoa,ward,parish,constituency,la}`
targets) and deployed to the blob store as `bounds_{level}/v1/{code}.geojson`.
If a boundary file is missing the map slot hides itself.
